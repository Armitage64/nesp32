How ping becomes input delay

Each console holds its own button presses back a whole number of frames so they can reach the other console in time. The nesp32 picks that number from the measured network time, between 1 and 5 frames. Past 5, the game waits on the network and slows down.

How it is worked out

delay = (rtt_us / 2 + 9000 + 16666) / 16667 // nesp_arq_ticks(), arq.c = ceil((one-way + 9 ms) / 16.667 ms), clamped to 1…5 // peer.c clamp()
  • The 9 ms is margin for the time between the controller read and the exchange with the nesp32 on each side. It is why a 0 ms network still costs 1 frame and why the first step comes at 15 ms of ping, not 33.
  • The ping fed in is not the average. During a game the nesp32 uses the delay that covers 90 in 100 of the round trips measured since the console's last report. A network with spikes is charted at its 90th-percentile ping.
  • The delay does not jump with every report. It rises after 2 reports in a row ask for more, and falls one frame after 8 ask for less. A session's first report sets it outright.
  • Past 148.7 ms of ping, 5 frames no longer cover the trip. The delay stays at 5 and the consoles wait for buttons, so the game runs slower than 60 fps. Here the chart follows the time the buttons need; the speed shown in the tooltip is an estimate of steady-state lockstep (5 ticks per one-way + 9 ms), not a measurement.
